## Этап 0. Доступ к API hh.ru (проверено 2026-09-24)

### Что проверяли и откуда знаем

| Источник | Что взяли |
|---|---|

Напрямую DNS не отвечает. Через тот же прокси `github.com` открывается. Внешний веб-фетчер тоже не достал hh.ru. Код ответа API пока не видели своими глазами. |

### Выводы

1. **Анонимно искать вакансии нельзя.** В описании `GET /vacancies` в спецификации сказано: «Если не передан токен авторизации, то после первого запроса будет предложено пройти капчу». Ответ `403` описан как «Требуется ввести капчу». В README hhru/api у поиска и просмотра вакансий стоят только пометки `client` и `employer`: нет ни `anonymous`, ни `applicant`. С апреля 2026 разработчики видят `403 Forbidden` на неавторизованный `GET /vacancies`. На dev.hh.ru между февралём и сентябрём 2026 убрали фразу «Личный кабинет вам не понадобится, если ваше приложение использует только поиск вакансий».
2. **Нужен токен приложения** (`client_credentials`). Получается через `POST https://api.hh.ru/token` или виден владельцу в `dev.hh.ru/admin`. Живёт бессрочно. Повторный запрос отзывает старый токен, запрашивать можно не чаще раза в 5 минут. Передаётся заголовком `Authorization: Bearer <token>`.
3. **Пользовательский OAuth соискателя не подходит.** В форме регистрации на dev.hh.ru написано: «поддержка API для соискателей прекращена 15 декабря 2025». У методов вакансий нет пометки `applicant`.
4. **Зарегистрировать приложение могут отказать.** К сентябрю 2026 из формы убрали выбор ролей, включая роль «Приложение». Заявку проверяют «несколько рабочих дней, в редких случаях до 15». По сообщениям на Хабре, ключи теперь дают в основном работодателям и рекрутинговым сервисам. Один разработчик в августе 2026 получил токен приложения, и поиск у него работает. **Это главный риск проекта.**
5. **Справочники доступны анонимно.** `/areas` и `/dictionaries` помечены `anon`, поддерживают `ETag`, `If-None-Match` и `Cache-Control`.
6. **User-Agent.** Обязателен заголовок `User-Agent`. Если HTTP-клиент не даёт его задать, можно отправить `HH-User-Agent`; при обоих заголовках берётся `HH-User-Agent`. Формат: `MyApp/1.0 (my-app-feedback@example.com)`. Ошибки: `400 bad_user_agent` со значениями `unset` или `blacklisted`.
7. **Лимиты частоты не опубликованы.** В спецификации есть только ответ `429 «Слишком много запросов»` у `GET /vacancies/{id}`. Заголовок `Retry-After` в документации не упомянут.
8. **Пагинация.** `per_page` не больше 100 (по умолчанию 10). Глубина выдачи не больше 2000: `per_page=10&page=199` работает, `page=200` вернёт ошибку.
9. **Капча** приходит как `{"type": "captcha_required", "captcha_url": ..., "fallback_url": ...}`. Ошибки авторизации — `403 oauth` со значениями `bad_authorization`, `token_expired`, `token_revoked` и `application_not_found`. Ответы 5xx могут прийти не в JSON.

### Решения

- **Только официальный API.** Никакого парсинга HTML, ротации User-Agent и прокси, обхода капчи. Так требует ТЗ. К тому же это единственный путь, который не нарушает условия hh и не сломается от смены вёрстки. Капча или 403 — сервер останавливается и объясняет причину.
- **Без токена не обращаемся к `/vacancies`.** Сервер сразу отвечает: «нужен токен приложения, положите `HH_ACCESS_TOKEN` в .env». Альтернатива — попробовать анонимно и остановиться на капче. Отказались: это заведомо бесполезный запрос, который провоцирует капчу на IP пользователя. Справочники запрашиваем и без токена.
- **Токен берём готовым из окружения**, сами его не получаем. Автополучение через `client_credentials` отзывало бы действующий токен и упиралось в лимит «раз в 5 минут». Ошибка `403 oauth` приходит с понятным текстом, что делать.
- **Отправляем и `User-Agent`, и `HH-User-Agent`** с одинаковым значением `career-mcp/<версия> (<HH_CONTACT_EMAIL>)`. Контакт берём из окружения. `HH-User-Agent` нужен по ТЗ, а `User-Agent` по документации основной. httpx иначе подставил бы своё `python-httpx/x.y`.
- **Лимит частоты — консервативный и настраиваемый.** hh не публикует цифр, поэтому ставим token bucket около 2 запросов в секунду с небольшим burst. На `429` соблюдаем `Retry-After`, если он пришёл, иначе делаем экспоненциальную паузу.
- **Для справочников поддерживаем `ETag`.** После истечения суточного TTL переспрашиваем с `If-None-Match` и получаем дешёвый `304`.

### Расхождения ТЗ с документацией hh

| В ТЗ | В документации | Что предлагаю |
|---|---|---|
| `schedule` в `search_vacancies` | `schedule` «заменён на параметры `work_schedule_by_days`, `work_format` и `employment_form`» | Параметр `work_format` (офис, удалёнка, гибрид), значения — из справочника |
| `only_with_salary` | «Заменен на параметр `label=with_salary`» | Оставить имя в инструменте, в API отправлять `label=with_salary` |
| `salary_from` | Параметр `salary` ищет вакансии, «вилка которых близка к указанной», а не «от» | Назвать `salary` и описать честно |
| Зарплата — `salary` | Есть новое поле `salary_range` с `mode` (месяц, час, смена…) и `frequency` | Статистику считать по `salary_range` и только по помесячным зарплатам, иначе почасовые ставки исказят медиану |
| `per_page ≤ 50` | API разрешает до 100 | Оставляем 50 по ТЗ: так ответ инструмента остаётся компактным |

Курсы валют: в `/dictionaries` у элемента `currency` есть поле `rate` — «Курс по отношению к рублю».

### Условия использования API — что важно для нас

- **П. 3.3.** Материалы можно использовать только по тематике сайта: «поиск работы, сотрудников, получение информации о рынке труда». Наш сценарий подходит.
- **П. 4.3.** Нельзя строить из данных базу для доступа других лиц. Кеш и шорт-лист локальные и однопользовательские, наружу не отдаются.
- **П. 4.6.** «Запрещается передавать данные, полученные посредством Сервиса …, сторонним сервисам для использования». **Это риск для LLM-части.** Отправлять тексты вакансий во внешний LLM-API — серая зона. Поэтому для `extract_requirements` по умолчанию используем локальную Ollama, внешний провайдер только по явному выбору в конфиге. Вопрос про Claude Desktop, куда MCP в итоге отдаёт данные, оставлен на решение владельца проекта.

### FastMCP: сверка с gofastmcp.com

- Актуальная версия — **FastMCP 4.0.7** (вышла 2026-09-23). Она построена на MCP Python SDK v2 (`mcp>=2,<3`) и требует `pydantic>=2.12`.
- Всё, что использует ТЗ, в документации совпадает:
  - `from fastmcp import FastMCP`;
  - stdio по умолчанию;
  - `mcp.run(transport="http", host=..., port=...)` с эндпоинтом `/mcp`;
  - тесты через `Client(mcp)` в памяти и `pytest-asyncio` с `asyncio_mode = "auto"`.
- **Конфликт зависимостей.** `langchain-mcp-adapters` 0.3.2 (последняя) требует `mcp<2`, FastMCP 4 — `mcp>=2`. В одно окружение они не ставятся. Решение: пример агента живёт в отдельном venv (`examples/requirements.txt`) и ходит к серверу по HTTP. По документации FastMCP 4 обслуживает и старые клиенты с рукопожатием. Проверим на этапе 7.
- Шаблонные ресурсы (`vacancy://{vacancy_id}`) в v4 по умолчанию проверяются на path traversal. Дополнительно проверяем, что id состоит из цифр.
